# Argus: User guide

For users: have your MRs reviewed by an existing Argus. Argus is deployed by the owner with Docker Compose; for installation and operations (owner/deployer) see [SETUP.md](SETUP.md). For the MR size limit and conventions for MR authors, see [MR-AUTHOR.md](MR-AUTHOR.md); you can share that page's link with colleagues directly.

Note: the Argus web UI is in Traditional Chinese. UI labels are given here in English with the original text in parentheses, so you can find them in the interface.

## 1. Login and approval

1. Open the Argus URL, click **Log in with GitLab** (「使用 GitLab 登入」), and authorize (scopes: `api`, `read_repository`).
2. A new account stays at "Awaiting approval" (「等待核准」). Meanwhile you can prepare your skill and thresholds under Settings (「設定」), but **reviews start only after the owner approves you**.
3. Argus reads MRs and publishes comments under your GitLab identity.

4. **Set your own Claude token** (next section). If it is not set, MRs assigned to you are recorded as "skipped" (「略過」), and Argus does not fall back to the owner's subscription.

## 2. Claude token (reviews run on your own Claude subscription)

Argus runs reviews on your own Claude subscription. It needs a long-lived Claude token:

1. On **your own computer** (with Claude Code installed), run:

   ```sh
   claude setup-token
   ```

   The browser opens an authorization page; after you approve, the terminal prints a token starting with `sk-ant-oat01-`, valid for 1 year. The command does not store the token anywhere, so copy it right away.
2. In Argus, go to Settings (「設定」) -> "Claude token", paste the whole line, and click **Validate and save** (「驗證並儲存」). Argus makes one real model call with it to confirm it works (limited to once per 30 seconds) and saves it only on success.
3. Afterward the page shows only "Set (date)" (「已設定（日期）」), "Not set" (「未設定」), or "Invalid" (「失效」), never the token itself. To change it, paste a new one (it replaces the old), or click **Delete Claude token** (「刪除 Claude token」).

**Good to know:**

- The token is stored encrypted on the Argus server and is used only to run reviews for you.
- Review usage counts against **your own** Claude subscription quota.
- You can delete the token in Argus at any time, or revoke the authorization at claude.ai; after revocation, Argus's reviews fail and the token is marked "invalid" (「失效」).
- The token is handed to that review's `claude` process only at review time (via an environment variable). It never appears in command-line arguments, logs, or error messages, and the review AI cannot see it. Each user's Claude config directory is isolated from the others.
- When the token is about 11 months old, the Settings page warns that it is about to expire; run `claude setup-token` again and replace it.
- If Claude rejects the token during a review (revoked or expired), Argus marks it "invalid" and later reviews are recorded as "skipped" until you paste a new token.

**Three credentials, do not mix them up:**

| Name | Looks like | Source | Purpose |
|---|---|---|---|
| Claude token | `sk-ant-oat01-...` | Your Claude subscription, generated by `claude setup-token` | Argus uses it to run reviews for you; usage counts against your subscription quota |
| Anthropic API key | `sk-ant-api...` | Anthropic Console | **Not used** in this version; pasting it into the Claude token field is rejected |
| Argus API key | `argus_...` | Generated on the Argus Settings page | Calling Argus's trigger API (section 4) |

Owner exception: when the owner has no personal token, the `claude` login inside the Argus container is used; when the owner has a personal token, the token is used. Members of the owner-designated test allowlist (`OWNER_ENGINE_TEST_USERS`) borrow the owner's login when they have no personal token.

> This version supports only Claude (the `claude-cli` engine). `codex-cli` is an experimental engine for the owner only and does not use your Claude token.

## 3. Settings

The "Settings" menu (「設定」):

| Item | Details |
|---|---|
| Upload SKILL.md file / paste skill content (「上傳 SKILL.md 檔案 / 貼上 skill 內容」) | Your review rules. Limit 200 KB; if both are given, the file wins; leaving the paste box empty keeps the existing content |
| Minimum severity (「最低嚴重度」) | `nit` < `minor` < `major` < `blocker`. Findings below the threshold, or without a line number, are not posted inline and are listed in the summary comment instead (the threshold only decides placement; it never hides content) |
| Minimum confidence, 0-1 (「最低信心值（0–1）」) | Same idea: findings below this value are not posted inline. Higher is more conservative |
| Diff line limit (「Diff 行數上限」) | An integer from 500 to 8000; leave empty for the default 2000. MRs above it only get a "please split" comment. The larger the limit, the easier it is to miss problems and the more likely a timeout (the review time limit scales with diff lines, up to 15 minutes); usage counts against your own subscription |
| Review language (「審查語言」) | A BCP-47 code such as `zh-TW`, `en`, `ja`; `zh*` uses the Chinese layout, anything else shows the summary headings in the English layout |
| Claude model (「Claude 模型」) | `CLI default` (`CLI 預設`) / `Opus` / `Sonnet` / `Haiku`. This is only a request; the model actually used is shown as "Most recently used" (「最近一次實際使用」) in the field's help text and in Review history |
| Also review MRs where I am the Assignee (「也審查 Assignee 是我的 MR」) | By default only MRs where you are the Reviewer are reviewed; when on, MRs where you are the Assignee are reviewed too. MRs you authored are not affected by this switch (use self-review for those). Off by default |
| Auto-approve (「自動 approve」) | See section 6; off by default |

**Skill warnings**: if a "Skill warning" (「Skill 警告」) appears after upload, it is only a reminder. The review agent is read-only; commenting, approving, and operating GitLab/Jira are done by the platform, so sentences in your skill that ask for those actions are ignored. The warning does not block saving.

## 4. How reviews are triggered

| Method | Details |
|---|---|
| Assigned as reviewer | Argus polls about every 30 seconds for open MRs assigned to you and reviews each new head commit once. Draft MRs are not reviewed |
| Assigned as assignee (optional) | After you turn on "Also review MRs where I am the Assignee" in Settings, open MRs where you are the Assignee are reviewed too (deduplicated against the reviewer list); MRs you authored are excluded. Off by default |
| Self-review (trigger API) | The author calls it after opening an MR to review their own MR with their own skill; drafts are allowed |
| New push | When the head commit changes, another round runs (incremental: only the diff since the last review; if the author merged the target branch into the MR, that round looks at the whole MR's changes) |

A given `(reviewer, MR, commit)` is reviewed only once; one reviewer's reviews run in sequence, while different people's reviews can run at the same time (the site-wide cap is set by the owner, default 3). Failed reviews are retried automatically, up to 3 times (after the 1st and 2nd failures, it waits 5 and 15 minutes respectively); if the 3rd attempt still fails, a note is posted on the MR, and afterward you can click **Re-review** (「重新審查」) on the Review history page. When the diff (excluding lock files, generated files, etc.) exceeds your limit (default 2000 lines), only a "please split" comment is posted and no review is done.

### Argus API key and the trigger API

1. Settings -> "Argus API key" -> **Generate Argus API key** (「產生 Argus API key」). The key (`argus_...`) is **shown only once**; store it in the environment variable `ARGUS_API_KEY`. Regenerating invalidates the old key immediately.
2. Call it (`self: true` = review your MR under your own identity):

```sh
curl -fsS -X POST \
  -H "Authorization: Bearer $ARGUS_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"mr_url":"https://gitlab.example.com/<group>/<project>/-/merge_requests/<iid>","self":true}' \
  http://<argus-host>:3000/api/trigger
# 202 {"queued":["<gitlab-username>"],"skipped":[]}
```

Without `"self":true`, it queues reviews for every approved Argus user who is a reviewer on the MR and has a skill. Reviewers without a usable Claude token appear in `skipped`, with the reason `no Claude token configured ...` or `Claude token invalid ...`. Response codes:

| Status | Meaning |
|---|---|
| 202 | Accepted; `skipped` lists anyone skipped and why |
| 400 | Not valid JSON / not an MR URL of this GitLab / the MR is not open |
| 401 | Wrong Argus API key, or your GitLab authorization expired (log in to Argus again) |
| 403 | You are not an approved user yet |
| 404 | Your GitLab account cannot see this MR |
| 429 | Limit of 30 calls per user per hour |

### Triggering automatically from your AI agent

If you open MRs with an AI agent such as Claude Code or Codex, you can have it ask Argus for a review after opening an MR or pushing.

1. Finish step 1 above first, and store the Argus API key in the environment variable `ARGUS_API_KEY` (e.g. in `~/.zshrc`). **Do not put the key in the repo, `CLAUDE.md`, or `AGENTS.md`.**
2. Make sure you have pasted your Claude token and uploaded a skill on the Settings page. When triggered with `self: true`, Argus reviews with your own Claude token and skill; if they are not set up, the review is skipped.
3. Add the following block to the project's `CLAUDE.md` (Claude Code) or `AGENTS.md` (Codex), and replace `<argus-host>` with Argus's address:

````markdown
## Argus automatic review

After opening an MR or pushing a new commit, ask Argus to review the MR:

1. After pushing, wait about 10 seconds (GitLab needs time to update the MR), then run:
   ```sh
   curl -fsS -X POST \
     -H "Authorization: Bearer $ARGUS_API_KEY" \
     -H 'Content-Type: application/json' \
     -d '{"mr_url":"<MR URL>","self":true}' \
     http://<argus-host>:3000/api/trigger
   ```
2. A 202 response means it was queued. If `skipped` says `already reviewed`, you probably called too early; wait a few seconds and call again.
3. The review result appears as comments on the MR (starting with `🤖 Argus`), usually within a few minutes. Fix the findings, push, and trigger again.
4. Do not run `/argus accept` yourself: whether to accept a finding is for me (the human) to decide.
5. Read `ARGUS_API_KEY` only from the environment variable; do not print it or write it to any file.
````

> **Why forbid the agent from running `/argus accept`?** The agent comments under your GitLab identity, and Argus treats the command it posts as your own ruling. Without the ban, the agent could mark the issues found in its own review as "accepted".

## 5. Reading review results

Argus posts one summary on the MR, and opens inline discussions for problems that have a line number and pass the threshold. The summary structure (labels are in Traditional Chinese on the MR):

| Section | Content |
|---|---|
| Header line | `第 N 輪 (commit) · 結論` (`Round N (commit) · Verdict`); the verdict is "Mergeable" (「可合併」), "Changes suggested" (「建議修改」), or "Needs discussion" (「需討論」) |
| Focus checked this round (「本輪重點檢查」) | The items specifically checked this round |
| Findings (「發現」) | Sorted by severity (blocker > major > minor > nit); inline ones keep a single line marked "see inline" (「見 inline」), the rest include the full explanation; nit is collapsed by default |
| Confirmed correct (「已確認正確」) | Items that were checked and found fine |
| Round tracking (「輪次追蹤」) | Only on re-reviews: of the N items from the previous round, how many are "fixed / still open" (✅ / ⏳), plus the number of new ones this round |
| Footer | `使用模型: ...` (`Model used: ...`; the actual model reported by the CLI; omitted if not reported) |

On a re-review, if a problem from the previous round is judged fixed, Argus automatically resolves the matching inline discussion and leaves a note (it only handles discussions Argus itself opened). Problems already reported are not posted again.

### Accepting findings: `/argus accept`

When you decide a finding needs no change (false positive, deliberate design, handled elsewhere), you can mark it "accepted" (「已接受」). It is then no longer listed as "still open" and does not count toward the verdict.

| Where the finding is | Command |
|---|---|
| Inline discussion | Reply in that thread with `/argus accept <reason>` (the reason is optional) |
| Item in the summary | Comment on the MR with `/argus accept #shortid <reason>`; the short id is the `#xxxxxx` next to each finding |

- Only you (the reviewer of that review) can accept; permission is determined by the GitLab note author. If anyone else issues the command, they get a reply and you are @-mentioned.
- It takes effect on the next polling cycle when the review queue is idle (usually about 30 seconds; later if the queue is busy), with no push needed: Argus replies "accepted" (「已接受」), resolves the thread, recomputes the verdict from the stored review result, and posts a note. **It does not re-run the AI**.
- After recomputing, if the auto-approve conditions are met (see section 6), it approves as usual; self-reviewed MRs are never approved.
- The verdict changes to "Mergeable" (「可合併」) only when there are no findings of minor or above left and the previous round's items are all handled; otherwise the AI's original verdict stands.
- In later rounds: accepted items are told to the AI along with the reason, with instructions not to re-report them in any wording; if the AI still reports the same item (same file, same title) it is filtered out; the summary shows "N accepted by reviewer" (「審查者已接受 N 項」).
- After a `/argus accept #id` MR comment succeeds, Argus resolves that comment; malformed or rejected comments are not resolved, so a human can see them.
- Each command is processed only once; a malformed command or an unknown id gets an explanatory reply. In Dry-run mode, it only records and posts no comments.
- The hint at the end of each finding tells the MR author about this flow and links to the [Guide for MR authors](MR-AUTHOR.md).

## 6. Auto-approve (optional)

Check "Auto-approve" (「自動 approve」) in Settings. After an actual (non-dry-run) review finishes, if **all** of the following hold, Argus approves **in your name** (and leaves a note stating that Argus did it):

- The verdict is "Mergeable" (「可合併」)
- This round has no findings of minor or above (nit is fine)
- All items from the previous round are fixed
- The MR author is not you
- It is not an author self-review (`self: true`)

Notes:

- If a later round no longer meets the conditions, Argus automatically withdraws **its own** approval and leaves a note; approvals that a human clicked are left alone.
- After you manually remove Argus's approval, Argus does not auto-approve that MR again. (Exception: if the project is set to "reset approvals on push" and the head has changed, it is treated as a reset caused by the push, and a clean round approves again; if that setting cannot be read, it is always treated as a manual removal.)
- The approval is bound to the reviewed commit; if the MR got a new push in the meantime, GitLab rejects it, which does not affect the review itself.

## 7. Review history

The "Review history" menu (「審查紀錄」) shows your latest 100 reviews, **grouped by MR**: multiple reviews of the same MR (e.g. from several pushes) are collapsed into one entry, newest MR first, collapsed by default; expand to see each round. "N records total" (「共 N 筆」) counts only the records within those 100; older ones are not counted.

- **Collapsed (summary row)**: shows the time of that MR's latest record (Asia/Taipei), the MR (clickable, opens in a new tab), the author (the GitLab account that opened the MR; older records show —), Commit, status (done / failed / skipped / running; dry-run has its own label; 「完成 / 失敗 / 略過 / 執行中」), Model, number of Findings, error, and "N records total / latest round M" (「共 N 筆／最新第 M 輪」; the round matches "Round N" (「第 N 輪」) in the summary comment).
- **Alert badges**: when that MR has failed records, records waiting for automatic retry, or records that can be re-reviewed manually (old failures already superseded by a later completed round are not counted; if the whole group has no completed round, all are counted), the summary row shows "N failed" (「有 N 筆失敗」), "N waiting for retry" (「N 筆等待重試」), or "Can re-review" (「可重新審查」), so you do not miss them even when collapsed.
- **Expanded**: lists every record for that MR (newest first): time, Commit, round, status, Model, Findings, error, and actions. "Will retry automatically at HH:MM" (「將於 HH:MM 自動重試」) and the **Re-review** (「重新審查」) button are on the corresponding record.

For the reason behind a "skipped" or "failed" status, see the "Error" column (「錯誤」).

## 8. Troubleshooting

| Symptom | What to do |
|---|---|
| Stuck at "Awaiting approval" (「等待核准」) | Ask the owner to approve you under User management (「使用者管理」). If the page says no owner is set, it is an installation problem; pass it to the owner/deployer (see Troubleshooting in [SETUP.md](SETUP.md)) |
| "GitLab authorization expired" (「GitLab 授權已失效」) at the top | Log in again as prompted; reviews are paused until you do |
| Review history shows "Skipped: Claude token not set yet" (「略過：尚未設定 Claude token」) | Set it up as in section 2. After that, the next cycle (about 30 seconds) reviews the same commit automatically; no new push needed |
| Settings or Review history shows the Claude token as "invalid" (「失效」) | The token was revoked or expired. Run `claude setup-token` again and paste it to replace the old one |
| Pasting a token shows "This is an Anthropic API key, not a Claude token" (「這是 Anthropic API key，不是 Claude token」) | You pasted an Anthropic API key from the Anthropic Console; use the token generated by `claude setup-token` instead |
| Assigned but not reviewed | Check whether you are approved and enabled, whether a skill is set, whether the MR is a draft, and whether the same commit was already reviewed; look at Review history and the `skipped` reason in the trigger response |
| Review history has entries but the MR has no comments | The row has the `dry-run` label: Argus is currently in Dry-run mode (reviews run, results are only recorded here, no comments are posted); ask the owner to switch to live mode on `/admin` |
| A warning appears when saving a skill | See section 3; it is only a reminder |
| Lost the Argus API key | It cannot be recovered; generate a new one and update your scripts |
| trigger returns 401 / 403 / 404 / 429 | See the response code table in section 4 |

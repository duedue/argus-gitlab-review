# Argus — Design Decisions

Decided 2026-10-01 via design interview. Source of truth for scope; change here first.

## Goal

Self-hosted multi-user GitLab AI code review platform. Each user imports their GitLab identity + review skill; when assigned as MR **reviewer**, the platform reviews automatically and posts comments under the user's identity.

## Decisions

| Area | Decision |
|---|---|
| Scope | Multi-user platform with Web UI from the start |
| Login / token | GitLab OAuth (`api` scope, auto refresh); tokens encrypted at rest; master key in macOS Keychain (local dev) / the compose `.env` (container). M2: PAT per user via CLI, AES-256-GCM encrypted. M3: OAuth login implemented (auth code + state + PKCE, refresh 5 min before expiry, rotated tokens persisted; refresh rejected => token invalid, re-login). PAT users keep their PAT; OAuth login of a PAT user only creates a session |
| Web UI (M3) | Hono + server-side JSX, no SPA. New users are **pending** until the owner approves; sessions in SQLite (hashed id, 7d), CSRF token on every POST, CSP `default-src 'self'`. `npm run web` runs server + poller in one process (single refresh-token writer) |
| Trigger | Webhooks cannot reach a self-hosted Argus on a private network, so: (1) polling every 30 s (`POLL_INTERVAL_SEC`) as the zero-integration fallback, (2) instant review via `POST /api/trigger` with a per-user API key (sha256 stored, shown once), called by the MR creator's agent/CLI. Poller and trigger share one in-process queue (per-user lanes, see "Concurrency (0.2.0)"), deduped by `(owner_id, mr_id, head_sha)`; `claimReview` is the final gate |
| Assignment | `reviewer` field by default. Per-user opt-in `users.review_assigned` (default 0) also polls `assignee_id=<me>`: merged with the reviewer list by MR `id`, and MRs authored by the user that come only from the assignee list are dropped (self-review stays on the trigger API). The trigger API and retry sweep are unaffected |
| Auto-approve | Per-user opt-in (`auto_approve`, default off), deterministic code only. Live run + verdict approve + no finding >= minor + no unfixed previous item + author != user => `POST /approve` with the reviewed `sha`, plus a note. A later non-clean round revokes only approvals Argus tracked itself (`auto_approvals`); human approvals are never touched. Best-effort, never fails a review |
| Project allowlist | Per-user **strict** allowlist (changed from the first cut, where empty meant everything). `users.review_projects` (TEXT, newline-separated, normalized: trim, strip leading/trailing `/`, lowercase, dedupe) and `users.review_all_projects` (INTEGER 0/1). Rule, pure `projectAllowed(path, list, allowAll)` in `src/projects.ts`, wrapped by `reviewAllowed` below: `allowAll` passes everything; otherwise only a list match passes, so an **empty list reviews nothing**. Entry `a/b` matches project `a/b` and `a/b/**` on a segment boundary (`a/bc` no), case-insensitive; an unparseable path fails closed. Filters **automatic** reviews only: the poller (reviewer + assignee lists) does not enqueue outside MRs, the trigger API in non-self mode puts the reviewer in `skipped` (`project not in user's review list`, also when the list is empty and allowAll is off), and the retry sweep drops (`clearRetry`) a non-self failed row whose project is no longer allowed (the poller would not re-claim it, so keeping it would retry forever). Self-review (`opts.self` / `self_review=1`) and the accept watch are never restricted. Outside MRs are silent: no MR comment, no `reviews` row, one `[poll] ... N skipped` log line per cycle. The project path comes from the MR `web_url` (`parseMrUrl`, now in `projects.ts` to avoid a review/trigger import cycle), no extra API call. **Migration:** `review_all_projects` is added with default 0 and, in the same `addMissingColumns` transaction and only when the column is being added, every existing **approved** user is set to 1 (they were reviewing everything; behavior unchanged; pending users start at 0 like new sign-ups). Web sign-ups start at 0, `bootstrapOwner` sets the owner's to 1 (a fresh install creates the owner via OAuth); `addUser` (owner-driven CLI `user add`) inserts 1 and never touches it on conflict. **Pending decisions and instant list (one-click allow):** the single rule is `reviewAllowed(db, user, path, mrId, authorId)` in `src/projects.ts` = author is the user (own MR: the user authored it and assigned themselves as reviewer, so dogfooding needs no list entry; such MRs are never recorded as pending, and since it is not a self-review row `mayApprove` still refuses to approve an author's own MR) `||` `projectAllowed(...)` `||` the MR is in `allowed_mrs`; the poller, the retry sweep and the non-self trigger all call it, so there is one place to change. `seen_mrs(gitlab_user_id, mr_id, project_id, mr_iid, project_path, title, web_url, author, last_seen_at)` replaces `seen_projects` (which was dropped with `DROP TABLE IF EXISTS` in the schema init: it only fed a UI hint, so nothing is migrated): after each **successful** list the poller replaces that user's rows with this round's skipped set (so closed, unassigned or newly allowed MRs vanish by themselves; a failed reviewer list or a failed assignee list leaves rows alone, since the skipped set would be incomplete; a write failure is only logged). `/reviews` shows it as 「待你決定的 MR」 (hidden when empty or allow-all) with two plain form POST buttons (no JS, CSRF + session; the MR is resolved from the caller's own `seen_mrs` row by `mrId`, never from client-supplied project/iid): `/pending-mrs/:mrId/allow-mr` inserts into `allowed_mrs(gitlab_user_id, mr_id, project_id, mr_iid, created_at)` (review every push until the MR closes; no cleanup job, the rows are tiny) and `/pending-mrs/:mrId/allow-project` appends the MR's full project path to `review_projects` and drops that project's other pending rows (they join the next poll). Both then enqueue this MR immediately like the manual retry (runtime `getMr` must be open and not a draft; own limiter of 10/min/user, counted only just before the enqueue so lookup failures, closed/draft MRs and a missing engine do not use it up), and the decision is stored first, so when nothing can be queued (no skill, no engine, GitLab error, closed, rate limit) the PRG redirect (`/reviews?notice=<code>`, fixed texts keyed by code, the query never carries text) says it was allowed and the next poll reviews it. No MR comment, no external notification. The settings page lists the entries with a 「解除審查」 button each plus an add box: `/settings/projects/add` and `/settings/projects/remove`, and allow-project, all write through one `writeProjects()` (a transaction that re-reads the user row, merges the change and calls setUser/`parseProjectList` for validation, cap 100, so concurrent clicks cannot overwrite each other; remove normalizes with the same parser and reports a miss); the settings form no longer carries the list. `/static/settings.js` only updates the 「目前不限制」 note text from the checkbox vs. the saved state; the list dimming reflects the saved state only. `user set review_projects=a/b,c/d` (comma or newline) and the settings buttons both go through `parseProjectList` (max 100 entries, 255 chars each) |
| Exclusions | Skip Draft/WIP; diff > the reviewer's limit (per-user `users.max_diff_lines`, 500–8000, NULL = global default `cfg.maxDiffLines` 2000; legacy incremental fallback uses the same limit) → single "please split" note (zh-TW, links `/docs/mr`); glob-excluded lock/generated/vendor/`locales/**/*.json` (global `EXCLUDE_GLOBS`, no per-user override). Engine time limit: 10 min up to 2000 changed lines, then `10 min × lines/2000` of the actual diff, capped at 15 min (`reviewTimeoutMs`, passed via `ReviewInput.timeoutMs`; retry backoff unchanged); renames diffed with `-M` so a move is not counted as a whole-file add |
| Skill | Claude Code `SKILL.md` folder format; 1 user = 1 token + 1 skill; reserve `project_pattern → skill` column |
| Compatibility | Platform injects an output contract over the skill; import-time static scan warns (does not block) on conflicting instructions (e.g. calling GitLab tools) |
| Security boundary | Agent sees only shallow clone + diff, tools limited to `Read`/`Grep`/`Glob`, outputs JSON findings. **Token never enters agent context**; deterministic code posts comments |
| Engine | `ReviewEngine` interface, `claude -p`. Since 0.2.0 each user reviews on **their own** Claude subscription via a personal Claude token (see "Per-user Claude token (0.2.0)"); the owner's container login serves only the owner (when they set no token) and the test whitelist. **Test-only exception:** env `OWNER_ENGINE_TEST_USERS` (default empty) lists non-owner usernames that may borrow the owner's CLI engine when they have no token of their own; startup warning + `[owner-engine-test]` log tag |
| Output | Per-user `language` (default zh-TW) is injected into the contract so titles/bodies are single-language. Post comments directly, prefixed with 🤖 marker. `file+line` → inline discussion; rest → one summary comment |
| Findings schema | `{verdict?: approve\|request_changes\|needs_discussion, summary?, focus?: string[], checked?: string[], findings: [{severity: blocker\|major\|minor\|nit, file, line?, title, body, confidence: 0-1}], resolved?: string[]}`; missing verdict is derived deterministically (any blocker/major → request_changes); retry once on schema failure. Contract carries a calibration rubric (latent wrong behavior ≥ major; confidence ≠ impact; unjustified requirement deviation → minor + needs_discussion) and an anti-rubber-stamp rule |
| Publish threshold | Per-user configurable; default `severity >= minor && confidence >= 0.7`. Threshold only decides inline vs summary — every finding is shown with its full body |
| Re-review | Incremental diff since last reviewed `head_sha` (every `--depth=1` fetch, so no commit history: merges are detected via the recorded `reviews.base_sha` = `diff_refs.base_sha` of the last done review). If that merge-base differs from the current one (target merged into the MR), the round reviews the full MR diff (`base_sha..head`, = GitLab "Changes") and the size limit counts that diff, since the incremental range would include the target's commits; NULL on older rows keeps incremental; open threads / carried items / round numbering are unaffected; dedupe by `(owner_id, mr_id, head_sha)`; no-engine skips leave a `skipped` row that is re-claimable once an engine exists; never re-post existing comments. Auto-resolve: open inline threads opened by this platform as the owner are passed to the agent; only ids it verifies fixed (and not re-reported) are replied to + resolved by code. Every review posts a summary (`第 N 輪 (sha) · 結論`, findings by severity, checked list); re-reviews add round tracking (previous items fixed / still open, new this round), including summary-only items |
| Requirement context | Deterministic code fetches Jira issues (keys in MR title/description, max 3; summary + description + up to 2 linked summaries) via REST v2 and passes them as untrusted `requirements` text; the agent never sees the token. Owner-level config for now (`JIRA_URL`, token from env `JIRA_API_TOKEN` or Keychain `argus`/`jira-token`); off silently without a token; failures never fail a review. Per-user Jira tokens come later. The contract also tells the agent the MR description may be wrong and `checked` must be verified against requirements/realistic data, not restated behavior |
| Project context & self-planned focus | Agent gets no repo `.claude` settings (`--setting-sources user` stays), so deterministic code supplies context as untrusted data: repo-root `CLAUDE.md` (else `AGENTS.md`) read from git at the MR's **base** commit (so an MR can't rewrite the rules it is judged by; if the MR changes the file the prompt says so), regular files only, 16 KB cap with truncation marker, symlinks refused; the agent may Read files it references. No caller-supplied focus and no MR-description focus extraction: an external focus list was measured to narrow the review, so the agent plans its own. The contract makes the agent plan 3-6 riskiest aspects of the change (migrations/upgrade and empty/all-disabled states, run-once markers, startup-blocking or silent-drop failure paths, helper-only or revert-proof tests, sibling code paths), check each, and report them as optional `focus: string[]` (summary section 本輪重點檢查 / "Focus checked this round", omitted when empty). `checked` items must state scope; unconditional equivalence claims are forbidden |
| Engine selection (2026-10-02) | Which engine serves a user is an **explicit persisted field**, `users.engine` (`claude-cli` default \| `codex-cli`), set only by the owner (`user set <u> engine=...` or the owner-only `/admin` select, CSRF-protected). `engineFor(user)` switches on it: no fallback, no auto-detection from other dimensions. Both are subscription CLIs. Which credentials a `claude-cli` user runs on is decided by the rule in "Per-user Claude token (0.2.0)"; `codex-cli` stays owner / `OWNER_ENGINE_TEST_USERS` only (not extended: its Linux sandbox does not run in every container environment, see below). Dev override: `review ... --engine <name>` (dry-run only, never persisted) |
| `codex-cli` engine (**experimental**) | `codex exec` in the clone, same `buildPrompt` + skill + `OUTPUT_CONTRACT` + language, final message parsed by the shared `parseReview` (`--output-schema` makes the JSON reliable; nullable `line` is dropped before parsing). Equivalent of Claude's tool lockdown: `--sandbox read-only` (no writes/network for tool commands), `--ignore-user-config` + `-c mcp_servers={}` + an isolated `CODEX_HOME`/`HOME` (`DATA_DIR/codex-home`, holds only a synced copy of `auth.json`, so the owner's gitlab/jira MCP servers and plugins are unreachable), `--disable apps/plugins/browser_use/computer_use/...`, web search off, repo `AGENTS.md` not loaded, env allowlist (no tokens). `auth.json` is copied in before and back after each run so token rotation never strands the real login. Quality vs Claude is unproven; treat as a trial feature |
| Copilot engine (future option, no code) | No official agent CLI with read-only tool use exists, so it would need our own agent loop (model API + Read/Grep/Glob tools implemented by us), and the ToS for automated use of a Copilot seat is unclear. Revisit only if an official CLI or API-key route appears |
| Model & engine status (2026-10-02) | `users.model` (NULL = CLI default \| `opus` \| `sonnet` \| `haiku`) is a per-user setting for the claude-cli engine only; `--model` is passed only when set. The model that actually ran is a CLI-reported fact (`modelUsage` keys, primary = most output tokens), stored in `reviews.model` and surfaced in history, settings and the summary footer, never inferred. `/admin` (owner-only) has an engine status card (`claude auth status`, cached 60 s, email masked) and a rate-limited, CSRF-protected connection test. Owner bootstrap: env `ARGUS_OWNER` promotes only that username (case-insensitive) on its OAuth login and only while no owner exists; there is no "first login becomes owner" |
| Failure handling (2026-10-02) | Red row in UI + log. A restart releases (deletes) rows left `running` so the head is simply re-reviewed. A failed review is retried automatically: `reviews.attempts` (default 1) and `next_retry_at` (epoch ms); after attempt 1 / 2 it waits 5 / 15 min, and the poller/trigger atomically re-claim a due row (`status='failed' AND attempts<3 AND next_retry_at<=now`). After the 3rd failure it is final and ONE general MR note is posted (best-effort, never in dry-run; reason = first line only, URLs/paths/tokens stripped, ≤200 chars). `skipped` rows are never retried. **Retry sweep (2026-10-05):** the poller only re-claims MRs it lists (user = reviewer), so author self-reviews and unlisted MRs would never retry. `reviews.self_review` (default 0) records a self-trigger claim; after each user's listing every poll cycle sweeps that user's due failed rows (engine required): fetch the MR with the user's runtime; not open or head moved past the row's sha -> `next_retry_at` cleared (final, no note); else queued through the shared queue (deduped by owner/mr/sha, `claimReview` still the atomic gate) with `selfReview` restored from the row, so a self-review retry can never auto-approve. The final note path is unchanged (once, live only). Manual: `POST /reviews/:id/retry` (row owner or Argus owner, session+CSRF, 1 per 30 s) resets attempts and queues the MR's current head if it is still open (self-review mode restored from the row) |
| Publish mode (2026-10-05) | Dry-run vs live is an **explicit setting**, not inferred. Precedence: env `DRY_RUN` set (non-empty; only `0` = live) = locked, wins > DB `settings.dry_run` > default dry-run ON. `cfg.dryRun` is the one effective value; its only writers are `loadConfig`, `applyStoredSettings` (startup) and `setDryRun` (the single write path: persists, then updates the running config, so it applies to the next review without a restart). `reviewMr` snapshots it once so a toggle mid-review cannot split a review across modes; dedupe/retry/round rows stay keyed by the mode at claim time. Owner-only `POST /admin/dry-run` (session + CSRF); going live needs a server-validated confirm checkbox; refused when env-locked (the card says how to unlock). The compose `.env.example` leaves `DRY_RUN` empty (empty counts as unset). CLI `review` still forces dry-run. Limit: a separate `cli loop` process reads the setting only at start |
| Accepted findings (2026-10-05) | A reviewer can accept a finding as-is. **Permission:** only the review row's owner (the identity Argus posts as; on a self-review that is the author), checked by the GitLab note `author.id`, never by note text. **Commands** (strict, at note start): in our inline thread `/argus accept [reason]`; elsewhere `/argus accept #<6-12 hex> [reason]`. Every finding shows a visible short id (first 6 of the sentinel fingerprint) and a hint line naming the reviewer and linking `/docs/mr`. **Storage:** human decisions live in `accepted_findings` (owner, mr, dry_run, sentinel, reason, accepted_by, note_id, announced), never in `findings_json` (AI output stays unmodified); `accept_notes` records every answered command note (accepted or refused) so each is handled once across restarts; both keyed by mode like review rows. **Effect (immediate, no AI run):** reply + resolve the thread, recompute from the latest done row (its findings, plus the previous items it left open, stored as `findings_json.unfixedPrev` from now on, plus our still-open threads) minus accepted, post one note (`已接受 N 項，剩 M 項，結論更新為：…`), then `syncApproval` as usual (self-review never approves; skipped when the head moved since that row). The queued job re-reads the latest done row and the MR itself, so a review that finished while it waited is the recompute base (never stale data, never an approve of an older sha). **Announce:** `announced` is set only after the verdict note succeeded (or by a review round, whose summary already reflects the accepts it subtracted); unannounced accepts (failed note, crash between claim and note) are recomputed and announced on the next cycle, exactly once. Rows written before `findings_json.unfixedPrev` existed (legacy) are watched even when their stored findings look empty, since their open inline threads are only visible on GitLab. Verdict lift rule: approve only when nothing blocking remains under the auto-approve gate's definition (no finding >= minor, no unfixed previous item); otherwise the stored AI verdict stands. **Later rounds:** the AI is told the accepted items (`ReviewInput.accepted`, same channel as the open threads: file, line, severity, title and the reviewer's reason as untrusted text, looked up from stored findings/summary items, else our thread on GitLab for legacy rows) with the instruction never to re-report them under any wording, only a NEW different problem at that place; accepted ids are also dropped from `prev`, from the AI's open threads and from its findings (same fingerprint = file+title) as the second line of defence; the summary shows the accepted count. A handled top-level command note (its own resolvable discussion) is resolved best-effort (live only); refusals stay open for humans. Refusals (non-reviewer, bad format, unknown/ambiguous id) are replied to; with several Argus reviewers on one MR, commands in another reviewer's thread or for its ids are left to it, and unattributable errors are answered only by the lowest user id among them. **Detection:** commands usually come without a new commit, and self-review MRs are never in the reviewer listing, so each poll cycle (after reviews + retry sweep, own try/catch: a failure is one log line and never stops the cycle) watches MRs whose latest done review (last 30 days) still has unaccepted items. API cost per watched MR per cycle: 0 calls if the MR is in this cycle's reviewer listing (its `user_notes_count`/`updated_at` is the stamp), else 1 `GET` MR; discussions are read only when the stamp changed (our own replies cause one extra read). Closed MRs are remembered and skipped; the stamp memo is in-process, so a restart costs one discussion read per watched MR (the DB guarantees no duplicate handling). Trade-off vs. reading discussions every cycle: far fewer paged calls, at the price of one extra GET for unlisted MRs; vs. events API: no per-project fan-out. Runs through the shared queue so it never interleaves with a review of the same user. Dry-run records decisions but posts/resolves/approves nothing (log only). Our still-unresolved threads of accepted findings are resolved again (resolve only, no second reply, never in dry-run; failures logged) by every later accept job and every review round, so one failed resolve cannot leave a thread open forever; for that, MRs with any accept stay watched (stamp-gated, so no discussion read without new activity). Limits: a failed reply is only logged, not retried (the accept itself holds and later rounds filter the item); a crash between the verdict note and `syncApproval` skips that approval until the next review round; re-reports are prevented by telling the AI (first line) and filtered by fingerprint (second line), so a reworded re-report the AI still makes slips through as a new item; MRs older than the 30-day window are watched again after their next review |
| Per-user Claude token (0.2.0) | **Source:** each user runs `claude setup-token` on their own machine (1-year OAuth token, `sk-ant-oat01-…`; the CLI itself recognises OAuth tokens by the `sk-ant-oat` prefix) and pastes it on their own settings page. Format check before anything else: an Anthropic API key (`sk-ant-api…`) or anything else is rejected with a message that never echoes the input. Then one minimal `claude -p` with the token (1 per 30 s per user); a 401 refuses the save, other errors save with a warning. **Storage:** `users.claude_token_enc` (AES-256-GCM with the master key, like the GitLab token), `claude_token_set_at`, `claude_token_invalid`; the only writers are `setClaudeToken` (set/replace, clears the flag), `clearClaudeToken` and `markClaudeTokenRejected`; not in the `user set` whitelist (no token in argv/shell history). The UI shows only set (date) / not set / invalid / owner login; `/admin` shows the same status per user plus the latest review (one query), never a token. Users are told (settings + USER-GUIDE) that the owner can technically decrypt it with the master key, usage counts on their own subscription, and they can delete it or revoke it on claude.ai. **Delivery:** decrypted only when the `claude` child is spawned and passed as env `CLAUDE_CODE_OAUTH_TOKEN` (Claude Code docs: auth precedence #5, below API-key env vars, which the env allowlist never passes) to that one child; never argv, never logged; any CLI error text is scrubbed of it. Each token user gets an isolated `CLAUDE_CONFIG_DIR` = `HOME` = `DATA_DIR/engines/<gitlab id>/claude` (0700), so the owner's container login (and its 401 disk-recovery path) is never reachable; `--strict-mcp-config --setting-sources user` and the Read/Grep/Glob tool lock are unchanged. **Engine rule** (one function, `chooseEngine`, used by the poller, trigger, settings, `/admin` and the queue lane rule): token set → that token (owner included); token flagged invalid → no engine (no fallback, owner included); no token → owner: container login, `OWNER_ENGINE_TEST_USERS`: owner login, everyone else: no engine. **No engine** = a `skipped` row with the reason (`尚未設定 Claude token…` / `Claude token 已失效…`), recorded once per head; `claimReview` replaces exactly these rows (DELETE + INSERT in one transaction, so the claimed row is a new latest row with a fresh `created_at`: history order, `/admin`'s latest review and the accept watch's 30-day window see it as new) and `reviewExists` ignores them, so a head is reviewed as soon as the user sets a token, without a new push. **Invalid:** `claude -p --output-format json` exits 1 with `api_error_status:401` on a rejected token; that review fails with a fixed message and the flag is set keyed by the exact ciphertext used (a token replaced meanwhile is never flagged). **Expiry:** estimated as set date + 365 days; settings and `/admin` warn from 30 days before |
| Concurrency (0.2.0) | One in-process queue with a **lane per credential**, decided by `laneFor` (derived only from `chooseEngine`, used by every enqueue: poller, retry sweep, trigger, manual retry, accept watch). Personal-token users (and no-engine users, which only record a skip) get their own lane (GitLab user id). Everyone running on the owner's **shared login** (`claude-owner-login`: the owner without a token and `OWNER_ENGINE_TEST_USERS`; `codex-owner-login`: the shared `auth.json` that `syncAuth` copies in and out) shares ONE lane, so two CLI processes never use, refresh or sync the same credential at once. Within a lane: a user's jobs (reviews from poller / trigger / retry sweep / manual retry, and their `/argus accept` jobs) run strictly in enqueue order, one at a time; different users run in parallel up to a global cap (env `REVIEW_CONCURRENCY`, default 3). Guarantees kept: queue-key dedupe while queued/running; `claimReview` stays the atomic DB gate (better-sqlite3 is synchronous, each claim is one statement); an accept job never interleaves with a review of the same reviewer (same lane rule; a lane change only happens when the user sets/deletes a token or the owner edits the whitelist, and the accept job re-reads the latest done row anyway), and it re-reads the latest done row when it runs. `pollOnce` runs users concurrently and awaits each user's reviews, sweep and accept watch in order, so a cycle ends when every user's work is done (the next cycle waits for the slowest user). The git checkout is the agent's cwd for the whole review, so clones are per reviewer (`DATA_DIR/clones/u<id>/<project>`); one lane = one job per clone at a time. Reviews of the same MR by two different reviewers may now run at the same time; they touch only their own rows, threads and approvals |
| Clone cleanup | Clones are never gc'd and each review fetch adds ~one snapshot-sized pack (a single clone reached several GiB across dozens of packs within a month; N reviewers = N copies), while deleting a clone only costs one shallow fetch (seconds) on the next review. So `pruneUserClones` (`repo.ts`) deletes `clones/u<id>/<project>` when idle > 14 d (mtime of `.argus-last-used`, touched by `prepareDiff`; an unstamped legacy clone is stamped, i.e. gets a full grace period) or pack bytes (`.git/objects/pack`) > 1 GiB; `clones/u<id>` of users no longer in the DB are removed too. Safety comes from the queue, not from locks: each user's cleanup runs as a job in that user's own lane (`laneFor`, so lane 0 for owner-login users, which then also waits behind other lane-0 reviews), hence serialized with their reviews, triggers, retries and accept jobs; the orphan sweep drains lane 0 and the user's own lane before deleting. At most once per hour per user (in-memory throttle, driven from `pollUser`; the first cycle after a restart runs it). Anything not matching `u<digits>/<digits>` is logged and left alone. Best-effort: failures are logged and never break a poll or review. Known limit: a lane change mid-review (user sets/deletes a token) is the same pre-existing edge as for review concurrency. While Argus is in OAuth setup mode, `pollCycle` skips OAuth users, so their clones are not pruned (by idle or size) until setup completes; they are still never treated as orphans (the orphan sweep uses the full DB user list). Setup mode is short and fetches nothing, so this is accepted. `prepareDiff` also logs the fetch-phase duration per review. Not done (out of scope): shared object store / alternates |
| Stack | TypeScript full-stack + SQLite, shipped as a Docker image run by Docker Compose |
| Deploy | Two modes (`ARGUS_DEPLOY`, explicit, never inferred): `compose` (set by `docker-compose.yml`; operator commands shown in the UI are `docker compose ...`) and `local` (developer, commands run directly). Unknown values fall back to `local` with a warning. `GITLAB_URL` is required (no default) and checked at startup; `JIRA_URL` is optional (unset = Jira context off). |

## Branch review history

Pre-MR branch reviews are stored (A), attached to the MR when it is opened (B) and optionally started by pushes (C). All three are implemented. Decisions: retention 90 days; attach posts the summary only and never feeds auto-approve; match = owner + project + head SHA + MR target branch == the review's base, done reviews only; push events polled via the events API; per-user daily cap default 20; push debounce 5 minutes.

**Data model.** `branch_reviews` (additive `CREATE TABLE IF NOT EXISTS`): `id TEXT PK` (the job uuid, also the API id), `owner_id`, `project_id`, `project_path`, `branch`, `base`, `merge_base`, `head_sha`, `status` (`queued|running|done|failed`), `verdict`, `findings_json` (`{findings, belowThreshold, lines, files, model, skipped}`), `summary`, `error`, `trigger` (`api|cli|push`), `created_at`, `finished_at` (epoch ms). `pushed_branches` holds the push trigger's per-branch state (latest head, push time, handled head, attempts). Users get `branch_daily_cap` (default 20) and `review_pushed_branches` (default 0). Everything is additive.

**Separation from `reviews`.** `reviews` UNIQUE(owner_id, mr_id, head_sha, dry_run) is the MR claim/dedupe, keyed by an MR id a branch does not have. `branch_reviews` has its own table and dedupe, and `branchreview.ts` imports no publisher and no claim functions. The only bridge is B, which reads `branch_reviews` and writes a normal `reviews` row through the existing claim path.

**A, persist.** The API job store is the table: POST inserts `queued`, the queue callback moves it to `running`/`done`/`failed`, GET reads the row (owner-scoped). Single-active rule: a `queued|running` row of the owner counts, except `trigger='cli'` rows (CLI runs bypass the queue, so a killed run would leave an orphan; the hourly sweep marks CLI runs still running after 20 minutes `failed`/`interrupted`). No age bound for queue-owned rows: the queue always finishes them and a restart marks leftovers interrupted. Startup marks leftover active rows `failed` (`interrupted`). CLI runs are recorded with `trigger='cli'`. Retention: finished rows older than 90 days are deleted by the hourly orphan sweep (`pruneOrphans`), which also deletes `pushed_branches` rows of users who opted out or no longer exist. List helper `listBranchReviews` (newest first, keyset pagination, up to 101 rows so the API can detect a next page) and `GET /api/branch-reviews`; the list parses each row's `findings_json` only to count (fine at page size; store counts in columns if lists get large).

**B, attach on MR open.** Two entry points, one function. (1) `reviewMr`, after the claim and the `diff_refs` wait: when the MR author is the user, the MR has no review history (`nextRound == 1`, otherwise a normal review runs so tracking, carried items and accepted findings are not reset), and `findDoneBranchReview(owner, project, head, target branch)` hits a non-`skipped` review, the stored result is published with `summaryOnly` (no inline threads: positions come from a merge-base diff that may differ from the MR diff) and `ctx.preMr`, which adds a quoted line to the summary (branch head, merge-base, base, review time; "not re-run on this MR"). The `reviews` row is finished `done` and, in the same transaction, `branch_reviews.attached_review_id` (additive, indexed) is set to that row's id, so the same head is never reviewed again, a later head reviews normally, and the UI link "-> !MR" (`attachedMrs`, one indexed join per page) shows only for the attached branch review. One sha throughout: the lookup uses the claimed sha and no attach happens if the MR head moved since the listing. `syncApproval` is never called on this path (no approve, no revoke). (2) The poller: `pollUser` does not review the user's own MRs, so after the reviewer/assignee MRs it runs `attachAuthoredMrs`: while the user has a done, attachable (has a verdict, i.e. not `skipped`) branch review with `attached_review_id IS NULL` (partial index, plain lookup) it lists their open authored MRs updated since the oldest such review STARTED minus 10 minutes (`updated_after`; an MR opened while the review ran is updated before it finished; ceiling: only reviews up to 14 days old count, so the gate closes then; a review whose MR is never opened costs one narrowed list per cycle for those 14 days, and an MR opened later no longer attaches), skips heads that already have a review row, applies the project allowlist (`projectAllowed`), requires a matching done branch review and round 1, and calls `reviewMr(..., {attachOnly: true})`. Attach-only never starts an engine run: with nothing to attach the claim is released and the MR is left alone (authored MRs are not opted in to reviews), so a branch review finished later can still attach. A failed attach (e.g. GitLab 5xx while posting) releases the claim instead of recording a failure, so no retry-sweep review or failure note can happen on an authored MR; the next poll retries the attach, up to 3 failures per (owner, MR, head) in memory, then it gives up until the head changes or Argus restarts. If the note was posted but finishing the row throws, a retry can post a duplicate summary (rare, accepted). The whole attach step is wrapped so its failure never skips the retry sweep, accept watch or push trigger.

**C, push trigger (`src/pushreview.ts`).** Opt-in `review_pushed_branches=1` and `branch_daily_cap>0` (0 = off); otherwise no GitLab call. At the end of each `pollUser` cycle: fold the user's push events (`/users/:id/events?action=pushed&after=<today-2>`; `after` is exclusive, so the real lookback is yesterday and today, 1-2 days; newest first) into `pushed_branches` (a changed head resets the push time and attempts), so the 5-minute debounce needs no timer. A row is due once its push is 5 minutes old and its head not yet handled. If the user's lane has queued/running work nothing starts (lane 0 serializes everyone, so push reviews wait rather than queue around MR reviews; ceiling: constant MR traffic on the shared lane delays them, they are not dropped). Per due row, cheapest first: daily cap (rolling 24h of `trigger='push'` rows; hit = stop and retry later, logged once per day) -> project allowlist -> default branch -> dedupe on any `branch_reviews` row of (owner, project, head, base = the project's default branch; any trigger/status) -> open MR on the branch -> tip still equals the pushed head -> `startBranchReview(..., "push")`. Definitive outcomes (not visible/404, not allowed, default branch, has MR, moved, project not found) mark the head handled and log the reason once; transient GitLab errors (5xx, timeouts) are retried next cycle, 3 attempts then handled with a log line; config problems (401, no engine, no skill) wait without using attempts (logged once per head) and end the cycle's push work (same for every branch); `too_many_active` just waits. One start per cycle. Results are only stored; they reach GitLab only through B. Ceilings: pushes older than yesterday at first sight (long downtime) are not picked up; failed push reviews are not retried; one events request per user per cycle (no webhook is used).

**Staleness.** A stored review is about its `head_sha`. The UI shows that head; there is no automatic invalidation when the branch moves.
